## Decisions

- Fumadocs is the project memory for implementation state, analysis, and contributor context.
- The chain must be flexible and configured externally, not hardcoded to a Muffin or any single pedal.
- Pedals and amps keep private DSP memory private.
- Shared electrical behavior is passed through an explicit chain state.
- Monitor tests should render to WAV rather than only writing to a null output.
- WAV comparisons should have a notebook view for visual inspection of
  alignment, residual energy, spectra, envelopes, and segment band errors.
- Reverbs are split by validation type: Springfield is the current spring
  graybox/IR hybrid, while StudioVerb is an original digital room/plate FDN
  effect for `all-nox`.
- The desktop frontend remains Rust-native with `iced`; premium plugin-style
  visuals should be built as custom-painted canvas scenes/components rather
  than standard widgets with light styling. The first direction check compiles
  with `cargo check -p greybound-desktop`.
- The desktop UI's first premium scene should default to the focused
  `grey-nox` truth set: Minotaur, Nox30, Springfield, and the configured cab IR.
  Do not present broad integration-board placeholders such as compressor/OD/mod
  slots, and do not present StudioVerb in "greybox only" mode because it is an
  original digital reverb rather than a circuit graybox reference.
- The desktop UI should not present the Nox30 amp as a pedalboard slot. The
  amp is a first-class top-menu view with its own large control panel; the
  pedalboard view contains only pedal/effect slots.
- The desktop UI should not show the legacy bottom slider control strip or the
  old white chain legend icons. Pedal, amp, and cab controls belong directly on
  the skeuomorphic device surfaces, with mouse dragging handled by the canvas
  hit targets.
- Desktop visual controls are moving into a reusable component library. The
  first extracted component is a configurable knob renderer with label,
  normalized value, min/max, step, and skin; surrounding amp or pedal background
  color is intentionally owned by the parent visual surface, not the knob.
- Desktop layout should behave like a plugin panel, not a responsive app: use a
  fixed `1600x900` design surface and apply one uniform scale factor based on
  the window size, preserving control positions and proportions. The desktop
  shell corrects resize events back to the design aspect ratio so arbitrary
  window ratios do not create blank margins around the plugin surface.
- Desktop input/output VU meters are connected to live CPAL/CoreAudio telemetry
  in the desktop app. The runtime opens selected input and output devices,
  streams input channel 1 through the focused `grey-nox` chain
  (Minotaur -> Nox30 -> Springfield -> embedded Celestion IR), writes mono to
  output channels 1 and 2, and publishes RMS-derived meter levels back to the
  UI at about 30 Hz.
- The desktop Settings button now opens a functional Audio Settings panel with
  discovered CoreAudio input/output devices, selectable sample rate and buffer
  size down to 32 samples, channel choices, and runtime status. Changing input,
  output, sample rate, or buffer size restarts the live audio engine with the
  selected runtime configuration; unsupported low-latency buffers surface as
  runtime status errors rather than being silently coerced.
- Audio Settings is rendered inside a reusable dark modal component with a
  dedicated title bar, body area, separator line, and top-right close button.
  Future modal panels should reuse that component instead of hand-building
  standalone cards.
- Modal details should stay plugin-like: compact title bars, rounded outer
  corners owned by the modal shell, and no nested borders around select fields.
- The desktop footer is a full-width bar, not a floating pill. It should use a
  square-edged footer container rather than the generic rounded ghost container.
- The root plugin panel is also a full-bleed fixed surface and should use a
  square-edged app panel container. Rounded containers are reserved for real
  overlays, devices, fields, and controls.
- The top global control bar is a structural band like the footer, so it should
  also use a square-edged container rather than the rounded ghost container.
- The pedalboard stage should not draw a surrounding container/frame. Device
  visuals sit directly on the main panel background.
- On startup, the desktop app now treats `48 kHz / 32 samples / f32` support as
  the low-latency device heuristic. It scores compatible devices and prefers
  known pro/external audio interfaces such as Scarlett/Focusrite over integrated
  MacBook devices, then falls back to the system default if no low-latency
  candidate is available.
- The audio lab now has a first Rust MCP sidecar,
  `greybound-audio-lab-mcp`, using stdio JSON-RPC. The desktop starts it when
  the binary is available, routes sidecar stderr to
  `target/greybound-mcp/audio-lab-mcp.stderr.log`, and keeps live CPAL audio
  separate. Implemented tools can list assets, inspect rigs, render bounded
  WAVs with temporary control overrides, parse monitor/WAV health, call the lab
  comparison workflow, and summarize run metadata.
- The desktop top control bar no longer exposes `cable` or a duplicate
  `SPRING` mix as user controls. Cable capacitance remains a rig/lab parameter,
  and Springfield mix belongs on the Springfield pedal surface. The visible
  global controls are plugged into live audio: `INPUT` applies pre-chain gain,
  `OUTPUT` applies post-chain gain, and `IR MIX` blends between dry amp output
  and the cabinet IR convolution.
- Desktop pedal footswitches are direct bypass hit targets. Clicking a
  pedalboard footswitch selects that pedal and toggles its bypass state, which is
  then copied into the live `SignalChain` runtime controls.
- The desktop app handles window close explicitly. Iced's automatic close
  handling is disabled so `CloseRequested` can first set a shutdown state, drop
  the CPAL audio streams, drop the MCP sidecar, prevent meter ticks from
  restarting audio, and then call `iced::window::close()`.
- The desktop input VU meter now measures the post-`INPUT` gain signal entering
  the DSP chain, not the raw CoreAudio capture. Lowering the `INPUT` knob should
  lower both the actual chain drive and the displayed input level.
- The desktop output path is currently dual-mono on output channels 1 and 2, but
  the output VU is now represented as stereo L/R with separate meter
  accumulators so the UI matches the physical stereo output layout and can
  support future true-stereo processing.
- The desktop metronome should be specified and implemented as a runtime utility
  mixed into the live output after the guitar DSP chain. It does not belong in
  rig files or signal-chain topology. The V1 spec lives in
  `knowledge/architecture/desktop-metronome.mdx`.
- Desktop metronome V1 is implemented in the live app. The footer opens a shared
  modal with play/stop, BPM step, volume, and pan controls. The CPAL output
  callback owns a sample-clock metronome generator and mixes its stereo click
  after guitar DSP/output gain, so pan appears on the stereo output VU meters.
- The desktop tuner should be specified and implemented as a runtime utility,
  not a rig device. It should analyze a clean input-side signal rather than the
  processed output, so pedals, amp, Springfield, cab IR, and metronome playback
  cannot affect pitch detection. The V1 spec lives in
  `knowledge/architecture/desktop-tuner.mdx`.
- Desktop tuner V1 is implemented in the live app. The footer opens a modal
  with cents/Hz display, live/hold, output mute, and reference pitch stepping.
  A dedicated worker consumes a duplicated input-side ring buffer and publishes
  normalized-autocorrelation pitch readings through atomics; mute gates only the
  final desktop output bus.
- Circuit visualization now has a runtime semantic source of truth in
  `core/src/circuit_descriptor.rs`. Minotaur and Springfield expose
  descriptor graphs with stages, edges, control bindings, implementation
  references, and confidence labels. These descriptors are model-level circuit
  explanations, not PCB artwork or full SPICE netlists, and the desktop circuit
  view should consume them before the next visual rendering pass.
- The desktop pedal circuit view no longer draws an invented decorative PCB.
  `greybound-ui` now depends on `greybound` with default features disabled and
  renders Minotaur and Springfield directly from the runtime circuit
  descriptors: stage nodes, routed edges, control badges, confidence hints, and
  a greybox/IR-hybrid badge.
- For pedal-shaped tall circuit views, the renderer now first tries a
  two-terminal series-parallel graph layout before falling back to the generic
  Sugiyama-style layout. This better matches Greybound pedal descriptors with a
  signal spine, explicit split branches, a merge point, and an output path.
  Branch subpaths are distributed horizontally when they contain multiple
  components, so sequences such as `Drive -> Clip -> Smooth` or
  `Dwell -> Tank IR -> Splash -> Recover` use the available pedal width instead
  of collapsing into a vertical column. Generic fallback layers use even
  spacing rather than descriptor-authored reference coordinates.
- The circuit-view toggle icon now lives at the top-right of the stage canvas
  instead of the top navigation. It is a local display mode, while the top
  navigation remains limited to first-class views: pedals, amp, and cab. The
  amp view now also supports circuit mode by rendering Nox30 component
  boundaries from `NOX30_COMPONENT_BOUNDARIES` as a circuit-informed stage map.
- The desktop UI now has a runtime amp-implementation switch for A/B work. The
  stable default still loads `nox30`; the experimental option loads
  `nox30-experimental` and restarts the live audio engine. The experimental
  alias is intentionally bit-equivalent to stable until a focused amp-model
  experiment diverges it, giving the lab a controlled baseline for future
  comparisons.

## Open Questions

- Which rig fields should be added next without mixing runtime session settings into JSON5 rig files?
- Should shared electrical state be sample-block level only, or should some fields support slower control-rate smoothing?
- How much impedance interaction should be modeled in the first pass before adding circuit-specific refinements?
- Which monitor metrics should become hard test assertions versus human-analysis signals?
- Should `all-nox` remain an intentionally all-active stress rig despite severe
  full-board clipping, or should it gain a calibrated monitor-safe preset
  variant?
- Should the MCP sidecar get an in-UI health indicator and restart button, or
  stay invisible until a lab/debug panel is built?
- Should the desktop metronome also be available in offline renders, or remain
  desktop/live-only until a render use case is clear?
- Should desktop tuner V1 analyze raw input or post-`INPUT` gain? Current
  recommendation is post-`INPUT` for consistency with the input VU.

## Risks

- Over-modeling electrical state too early could make the chain hard to evolve.
- Under-modeling impedance and voltage behavior could make pedal ordering sound unrealistic.
- Monitor logs can become noisy unless every metric has a clear diagnostic purpose.
- Full-board `all-nox` renders can mask isolated pedal health because the
  aggregate chain clips even when an individual effect is stable.
